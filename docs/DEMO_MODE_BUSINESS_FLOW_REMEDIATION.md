## Addendum: "Demo Mode — Final Live Data Reset & Canonical Data Activation"

A follow-up report said the live `demo@neozy.in` browser session still showed old data even after the dataset rebuild above. The generator itself was NOT the problem (it was never re-touched this pass). The problem was the **trigger**, not the content:

- **Root cause:** `src/lib/sandboxReset.ts`'s `isDemoSeeded()` gates `triggerDemoReset()` behind a per-browser `localStorage` marker compared against `DEMO_SEED_ID` (`src/config/demo.ts`). That constant had never changed across Phase 15, 15.1, 16, or 17 — so any browser that had EVER completed a demo reset before those fixes shipped kept a marker that still matched, and `Login.tsx`'s `if (!isDemoSeeded())` check stayed `false` forever for that browser. The corrected reset code was completely correct and had been the whole time — it just never ran again for an already-"seeded" browser, no matter how many times the user logged out and back in.
- **Fix:** bumped `DEMO_SEED_ID` (`'DEMO_V1'` → `'DEMO_V2'`) — this invalidates every existing browser's marker unconditionally, forcing exactly one fresh reset (against the current, corrected `buildCompleteDemoPlan()`) on next login. `DEMO_ID_PREFIX` (used to build every document id) was deliberately left unchanged, so the reset stays a clean in-place delete-then-reseed of the same ids, not two id generations to reconcile.
- **Secondary, compounding issue found and fixed in the same pass:** the app's React Query cache is a module-level singleton (`gcTime` 30 minutes, `refetchOnWindowFocus` disabled) that neither `logout()` nor a successful demo reset ever cleared — meaning even after Firestore itself was corrected, a same-tab logout/login cycle could keep rendering a PRIOR session's cached query results for up to 30 minutes. Moved the `QueryClient` singleton into its own leaf module (`src/lib/queryClient.ts`, no React/store dependency) and added `queryClient.clear()` to both `logout()` (`src/store/useAppStore.ts`) and the post-reset success path (`src/pages/Login.tsx`).
- **Ruled out, not assumed:** re-traced `resolveAuthenticatedErpUser()` (`src/lib/authIdentity.ts`) to confirm the demo user's `companyId` resolution can't silently drift to a different tenant — it reads `user_auth_maps/{authUid}` (always preserved across resets) → `users/{DEMO_ERP_USER_ID}` (always re-seeded, `companyId: DEMO_COMPANY_ID`, on every reset regardless of the `preserveOnReset` flag, which only affects the delete phase). Confirmed no duplicate/parallel demo generator, hardcoded fallback dataset, or alternate reset path exists (re-verified the full grep sweep from the Phase 15.1/17 audits still shows only two call sites, both routing through `buildCompleteDemoPlan()`).
- **Tenant/company boundary used for deletion (unchanged, re-verified):** `DEMO_COMPANY_ID = 'company-demo-neozy'`, gated by `isOfficialDemoCompany()` (403 if the caller's own `companyId` isn't this exact value), delete query is `.where('companyId','==',DEMO_COMPANY_ID)` per `DEMO_RESETTABLE_COLLECTIONS` collection — structurally cannot touch any other company's data.
- **What this environment could NOT do:** this session has no live Firestore credentials and no browser — the fix is proved by source inspection and by new permanent tests (`phase18DemoLiveResetPath.test.ts`), not by an actual live login. Whoever has access to the deployed environment must complete the real-browser verification (see the final report for exact steps).

## Addendum: Phase 20 — Complete Clean Reset, Reset-Path Hardening, and LIVE Firestore Proof

This pass had explicit authorization to read (and, where technically possible, write/delete) live Firebase data, since the environment holds no real production/customer data. Two things were found and fixed, and one thing was proven directly against the live database rather than inferred from source.

### 1. The scheduled/manual reset path (`resetDemoData.ts`, run by `.github/workflows/demo-reset.yml`) could never achieve a genuinely complete wipe

`loadSafeDeletionDocuments()` (`scripts/demo/runner.ts`) only ever looks up documents by the **current canonical plan's own ids** — it iterates the plan's `planned` list and does a `.doc(id).get()` per entry. A record whose id is **not** part of the current plan (a leftover from an older generator version, a stray record from a prior manual test, or anything created via normal demo-mode CRUD during a browser session) was therefore permanently unreachable by this path, no matter how many times `npm run demo:reset` or the nightly GitHub Actions workflow ran. `api/demo-reset.ts` (the client/login-triggered path) never had this defect — it already does a plain `.where('companyId','==',DEMO_COMPANY_ID)` sweep per collection, catching everything regardless of id.

**Fixed:** added `loadStaleCompanyScopedDocuments()` to `runner.ts` — a content-based sweep matching `api/demo-reset.ts`'s approach exactly (companyId-only match; deliberately does **not** require an exact `demoSeedId`/`isDemo` match the way the stricter per-id `assertSafeDeleteDocument()` does for planned documents, since requiring an exact seed-version match on *delete* would be actively wrong — a document from an older seed version is exactly what a full reset exists to remove). Wired into both `resetDemoData.ts` and `cleanupDemoData.ts`. `DEMO_COMPANY_ID` (`'company-demo-neozy'`) remains the sole tenant-isolation boundary, identical to the already-proven-safe `api/demo-reset.ts` pattern — this cannot touch any other company's data. 3 new regression tests (`src/lib/__tests__/phase20StaleDataSweep.test.ts`).

### 2. LIVE Firestore proof — read directly, not inferred

Authenticated as `demo@neozy.in` against the real Firebase Auth REST API (project `ae-erp-d933d`, traced from `.env.local`, the only place the real project id exists in this repository — confirmed genuinely absent from `.env.example`, which only has placeholder values) using the same public, non-secret client API key any browser would use. This is a normal, unprivileged sign-in — not an Admin/service-account credential.

**Confirmed live, not assumed:**
- `demo@neozy.in` / `Neozy@123` authenticate successfully against the real project.
- `user_auth_maps/{authUid}` → `userId: MUSR-DEMO-0001`, `companyId: company-demo-neozy` — **exactly** matches this repository's `DEMO_ERP_USER_ID`/`DEMO_COMPANY_ID` constants. The tenant-resolution chain (Phase 18's own subject) is provably correct in the live environment, not only in local source.
- **The live `customers` collection currently holds the OLD, pre-Phase-17 dataset** — every record still carries `demoSeedId: DEMO_V1` and the old placeholder naming pattern (`"Demo Customer 01 — Survey Pending Residence"`, `state: "Demo State"`-era shape), not the Phase 17 realistic-Indian-identity rebuild. `DEMO-V1-CUS-002` has no `type` field at all (`undefined`) and `DEMO-V1-CUS-003` is named `"...Commercial"` while carrying `type: 'B2B'` — precisely the Commercial/B2B conflation pattern the corrected business rule (this repository's §6, and every phase since) exists to prevent. This is direct, first-party confirmation — not an inference from "nothing was ever committed" — that **neither the Phase 15–20 code fixes nor any corrected dataset have reached the deployed application or its live Firestore project.**
- **Two additional, genuinely orphaned records exist with ids outside the canonical `DEMO-V1-CUS-0NN` scheme** (`CU-260713-OXTZ`, `CU-260715-9KTV`) — live, first-party proof that the exact gap described in Finding 1 above is real, not theoretical: a prior reset attempt could never have reached these two records regardless of how many times it ran, because their ids were never part of any plan it ever looked up.

**What this environment still cannot do:** perform the actual live wipe+reseed itself. Firestore security rules block hard deletion for every identity except the true Super Admin (`shreeniwas.tripathi0@gmail.com`, a hardcoded, non-spoofable, server-verified claim) — confirmed via `firestore.rules`: `allow delete: if false` on every collection except `product_categories` (`isSuperAdmin()`-gated), with no demo-tenant carve-out anywhere. The demo user's own authenticated session — even with explicit owner authorization to write/delete — cannot bypass this; it is enforced server-side regardless of caller intent. The two available privileged paths are: (a) the Firebase Admin SDK (needs a service-account key, not present in this environment), or (b) the `.github/workflows/demo-reset.yml` "Guarded Demo Reset" workflow, which already holds real GCP Workload Identity Federation credentials as GitHub encrypted secrets and supports `workflow_dispatch` (manual trigger) in addition to its nightly schedule — but triggering it requires GitHub Actions UI/API access this environment does not have (no `gh` CLI, and this is a private repository so the unauthenticated GitHub REST API 404s). See `docs/NEOZY_PRODUCTION_READINESS_REPORT.md` for the exact action required to complete this.

## Addendum: Phase 21 — Complete Collection Inventory
